# Candidate performance trial (synthetic only)
Deploy only the candidate Worker after CI and operator approval. Do not change production, RTDB, credentials or dataset guard.
Baseline and after: use browser Network tab, record POST /v1/transition total duration and Server-Timing (auth, runner, firestore, total). Expo development console logs token acquisition and HTTP duration without IDs or payloads. Old deployment has no Server-Timing; use HTTP duration and record it as baseline. Record button-to-status time separately. Use same device/network, at least 5 confirm/cancel pairs, fresh synthetic orders (respect rate limits), compare median and slowest; verify stock before/after each and repeat requests do not change stock twice. Do not use customer data. A lost response must be reconciled by read, not automatic mutation retry. Local events refresh same-app views; other devices remain on bounded polling. No new service or shorter polling interval. Timing is not a live performance claim.

Additional diagnostics: fs_begin, fs_read, fs_query, fs_commit and fs_rollback measure each upstream request until response headers (including failed attempts); firestore measures the whole transaction including body decoding and retries. Do not sum overlapping parent and child durations. Identity verification and role checks remain uncached. Catalog invalidation on same-app order events is limited to possible stock changes; other-device changes still use bounded polling. Test the baseline on the existing deployment before updating the candidate Worker. No staging or production deployment is performed by this commit.

28 Nov incident: baseline N948415 confirmation returned HTTP 503 in 9.09 s. Exact upstream failure is unknown until deployed diagnostics or Worker logs identify the stage. The candidate now selects read-only transactions for read routes, keeps all mutations atomic and read-write, uses bounded backoff only on explicit ABORTED, and records fixed failure phase names in Server-Timing. An ambiguous write triggers an authoritative order read, never a second mutation. Read-only cleanup is best effort after a complete snapshot. Verify with real synthetic orders before claiming a fix. Record stock and order state before retrying any operation with an unknown outcome. Do not send request authorization headers or tokens in screenshots.
